# 写任务章节的完整流程

> 版本：本包 1.21.1 / NeoForge / FTB Quests 2101.1.38
> 适用：任何要动 `config/ftbquests/quests/chapters/*.snbt` 的活；L2「科技先锋」是完整例子
> 工具：`kubejs/tools/l2_design.py`（设计表）、`l2_layout.py`（布局）、`gen_l2_quests.py`（生成）、
> `check_quests.py` / `check_quest_text.py` / `check_snbt.py` / `check_js_rhino.py` / `lint_iu_l2_metals.py`（体检）
> 文案：`.github/skills/asd-ste100-zh/SKILL.md`（中文清晰写作规则）、`lint_quest_text.py`（中文文案体检），
> 用法与取舍见 §10

## 0. 一句话流程

口径（这一章讲什么）→ 设计表（一格一台机器）→ 布局（树形，0 交叉）→ 生成（写 snbt + 文案）→
校验（四个脚本）→ 配方配套（任务得有配方撑得住）→ 进游戏验收（reload 看形状）→ 记档（改文档）。

顺序不能倒：先有口径才有格子，先有格子才有坐标。**坐标永远是算出来的，不手填。**

## 1. 铁律（踩过的坑）

1. **不新建章节文件。** FTB 2101.1.38 会把新建文件里的 chapter / quest / task id 全部改写成随机值，
   并且丢掉 dependencies。要加一章，先把空壳章节并进包、进游戏 reload 让 FTB 生成一次，
   或者在已有空壳里填格（「第一小步」`25acb136e49b8bb8` 就是这么用的）。
2. **已发布的 id 不动。** 玩家进度挂在 quest id 上，改 id = 存档进度丢失。
3. **坐标不手填。** 手摆几十格必然交叉。坐标由 `l2_layout.py` 按依赖树算。
4. **一格一件事。** 一台机器、一道工序、一个材料门槛；两件事塞一格，读者不知道该造什么。
5. **任务必须有配方。** 写进任务书的物品，要么原包有配方，要么我们自己在 KubeJS 里补（见 §6）。
6. **主线一条，从左到右；支线上下分叉。** 跨章入口只一个，出口只一个，出口要接上下一章。
7. **文案照 DJ2 写，再按 asd-ste100-zh 消歧。** 短句、动词、一个东西只有一个名字，
   条件、风险、要求强度写在动作前，规矩和体检脚本见 §10。

## 2. 阶段一：口径

先写一段话：核心线是什么、出口是什么、支线有哪些、从哪一章进来、出口指向哪一章。
写进 `l2_design.py` 顶部的 docstring，并与 `QUEST_LINES.md` 的章节表保持一致。

判断标准：

- 主线每一格都是"不做就推不下去"；
- 支线是"不做也能收尾，但做了更舒服"（钼线就是这样：只服务 316L 与 M3 掩模，降成支线）；
- 出口必须是下一章的入口（铂锭 → 太空），不能是一格孤零零的成果。

## 3. 阶段二：设计表

文件：`kubejs/tools/l2_design.py`。一格一个元组：

```python
("cap", "5E0E000000000022", "5E0F000000000023", [ENTRY], 0.0, 0.0,
 "industrialupgrade:circuit/circuit_part1", 4, "",
 "电容：改良机的入场券", "一片晶圆换一块电路板",
 ["这是什么…", "为什么现在做…", "往后接什么…"]),
```

| 字段 | 含义 | 规矩 |
| --- | --- | --- |
| key | 图内短名 | 唯一，供 deps 引用 |
| id | quest id，16 位大写 hex | 已发布的绝不改；新格顺延未占用的号 |
| tid | task id | 与 quest id 一一对应，同段顺延 |
| deps | 依赖 | 同章写 key；跨章直接写别章的 quest id（如 `ENTRY`） |
| x, y | 占位 | 恒为 `0.0`，真坐标由布局算 |
| item | 图标 = 交付物 | 必须能被 `/give` 解析，写全 namespace |
| count | 交付数量 | 与配方产出一致：一次产 4 就写 4，别写 16 |
| shape | 格子外框 | `""` 默认，特殊格 `hexagon` / `circle` |
| title | 标题 | 带关键数字（`改良机壳 138`） |
| subtitle | 副标题 | 一句"为什么是这一步" |
| desc | 正文 | 三段式：这是什么 → 为什么现在做 → 往后接什么 |

取新 id 之前先确认号段没被占用（`5E0E…` 是 L2 的 quest，`5E0F…` 是 task）：

```bash
grep -o 'id: "[0-9A-F]\{16\}"' config/ftbquests/quests/chapters/*.snbt | sort -u | grep 5E0E
```

文案怎么写见 §10（句长、分号、术语、动词都有硬规矩）。

**一个图标只对应一格**：`--sync` 靠图标反查 id，图标重复就认不回来。

## 4. 阶段三：布局

`l2_layout.place(cells, step=X_STEP, axis="h")`：

- **深度** = 根到该格的最长依赖路径，只认 deps 的第一个（主父）；
- **叶子**按 DFS 顺序分竖向槽位，每片叶子占 1 格，父格居中于子格——树的标准平面画法，**结构上不可能交叉**；
- 摆完跑 `crossings()`：既查两段线相交，也查"一条线正好穿过中间的格子"。

调参：

| 参数 | 作用 | 现状 |
| --- | --- | --- |
| `X_STEP` | 横向（深度）间距 | `1.5` → 本章 19.5 格宽 |
| `Y_STEP` | 纵向（槽位）间距 | `1.8` → 本章 19.5 格高 |
| `axis` | `"h"` 深度向右 / `"v"` 深度向下 | `"h"` |

宽度 ≈（最长链长 + 1）× `X_STEP`，高度 ≈ 叶子数 × `Y_STEP`。要更窄就压 `X_STEP`（格子更挤），
要更扁就把长链拆成两条从同一格分叉——**不要用 `wrap` 折带模式**：试过 6~10 列折带，
每档都出 17~40 处交叉（跨带那条斜线会扫过别的分支），除非重写算法，否则不开。

交叉不为 0，按这个顺序处理：

1. 去掉那一格的"第二父"（并流线），把另一条来路写进正文；
2. 真要画两条线，就让两个父格落在同一层且相邻（双联齿轮机 = 挤出 + 裁切、镭射钻基座 =
   高级框架 + 镭射钻，就是这样摆的）；
3. 都不行就接受，生成时 `gen_l2_quests.py` 会把交叉喊出来。

## 5. 阶段四：生成

```bash
python kubejs/tools/gen_l2_quests.py            # 按设计表重写章节，保留已有 id
python kubejs/tools/gen_l2_quests.py --prune    # 一并删掉设计表里不存在的旧格
python kubejs/tools/gen_l2_quests.py --sync     # 格子 id 被 FTB 改写过时，按图标认回来
```

生成器做四件事：坐标注入 → 章节 snbt 写入（CRLF、浮点带 `d` 后缀）→ `lang/zh_cn.snbt` 补文案 →
id 冲突与孤儿依赖检查。

`--sync` 的原理：FTB 重写 id 时图标不变，于是拿 `图标 → 设计表` 反查，把章节里的 id 改回设计号，
deps 一起翻译。只对图标唯一的格子有效。

## 6. 阶段五：校验

```bash
python kubejs/tools/gen_l2_quests.py \
 && python kubejs/tools/check_quests.py \
 && python kubejs/tools/check_snbt.py config/ftbquests/quests/chapters/*.snbt config/ftbquests/quests/lang/zh_cn.snbt
```

| 脚本 | 管什么 | 失败了怎么修 |
| --- | --- | --- |
| `check_quests.py` | id 唯一、依赖有归属、坐标不重叠、依赖线不穿格不相交、文案缺口 | 重复 id → 换号；孤儿依赖 → 补格或删 dep；重叠或交叉 → 布局有问题（点章节名跑，交叉按失败算） |
| `check_quest_text.py` | 章节里已有任务的中文文案（读 `lang/zh_cn.snbt`） | 按 §10 改那一句；三章主线默认全查 |
| `check_snbt.py` | SNBT 语法（按 Minecraft 的宽松规则解析） | 多半是括号/引号，看报的行号 |
| `check_js_rhino.py` | 用包内 Rhino 解析 KubeJS 脚本（只验语法） | 语法错改语法；逻辑错看 `KJS_SCRIPT_RULES.md` 的桩测试 |
| `lint_iu_l2_metals.py` | 材料白名单（禁钛/钨/铂族/铝…） | 换材料，或确认它属于"出口专用" |
| `lint_quest_text.py` | 文案：句长、分号、术语、空话、动词 | 按报的那一句改，见 §10 |
| `check_js_balance.py` | 花括号平衡（**必须在 `kubejs/` 目录里跑**） | 少一个大括号 |

`check_quests.py` 的"文案缺口"会把别章旧任务也列出来，只要本次动过的格子不缺就算过。

## 7. 阶段六：配方配套

任务书写"这台机器要电解铜"，KubeJS 里就得真有这条配方：

- IU 的改在 `kubejs/server_scripts/industrial/iu_l2_improved_electric.js`；
- 其他模组（EnderIO 等）改在 `industrial/enderio_l2.js`；
- 改法固定：`event.remove(...)` 旧配方 + 用同 id 重写。材料优先用 tag（`#c:plates/stainlesssteel`），
  别写死物品，方便以后换；
- 自造材料（`kubejs:electrolytic_copper`）必须先有一条产出路径，否则任务书上的格子没有来源，
  玩家会卡死在这一格；
- 改完跑 `check_js_rhino.py`，再进 JEI 确认旧配方消失、新配方出现。

## 8. 阶段七：进游戏验收

1. `/ftbquests reload`（改 snbt 或 lang 之后都必须）；
2. 看四件事：章节顺序（`order_index`）、依赖线形状（应 0 交叉）、图标是否解析（紫黑格 = 物品 id 写错）、
   格子位置是否符合设计；
3. 如果 reload 后出现陌生 id（FTB 改写了）→ `python kubejs/tools/gen_l2_quests.py --prune --sync`；
4. 点开一格看文案：标题 / 副标题 / 正文三段是否都在（缺 = `lang/zh_cn.snbt` 没写进去）；
5. 配方侧：JEI 搜那几类配方，确认旧配方消失、新配方出现。

## 9. 阶段八：记档

改完更新 `kubejs/docs/QUEST_LINES.md` 的章节表（车道、格数、出口），以及模组文档对应小节
（如 `IU_L2_IMPROVED_ELECTRIC.md` §6.8 / §7）。文档是下一次改动的输入，不写等于下次从零开始。

## 10. 文案规矩（DJ2 语感 + asd-ste100-zh 清晰）

任务书的文案分两层管，别混在一起：

- **读起来像人写的**（DJ2）：第二人称、祈使句、短句、给数量，偶尔一句吐槽。
- **读不出第二种意思**（asd-ste100-zh）：条件、风险、要求强度、术语只有一个读法。
  技能在 [`.github/skills/asd-ste100-zh/SKILL.md`](../../.github/skills/asd-ste100-zh/SKILL.md)，
  动任务文案之前先按它过一遍。

优先级：用户当次的要求 > §10.1 的硬数值 > asd-ste100-zh 通则 > DJ2 的语感。
STE 的英文专属规矩（20 词、时态、短语动词、受控词典）不移植到中文，中文按技能里的中文规则走。
技能里的 `scripts/ste-lint.py` **只查英语**，输入含汉字时直接返回退出码 2（未检查）；
中文体检用本仓库的 `lint_quest_text.py`，不要拿前者给中文背书。

### 10.1 硬数值（`lint_quest_text.py` 全部机器检查）

| 规矩 | 数值 |
| --- | --- |
| 句子长度 | 标题、副标题 ≤ 20 字；正文每句 ≤ 25 字 |
| 分号 | 完全禁止（`；` 和 `;`） |
| 段落 | 一格最多 3 段 |
| 一个事物一个名字 | 见脚本里的 `TERMS`：电解铜、改良机壳 138、MFE 母线…… |
| 营销形容词 | 无缝、强大、稳健、极致、丝滑、卓越、赋能、助力、打造 |
| 空话堆砌 | 需要注意的是、值得一提、有助于、从而、有效地、可能会、总的来说、简单来说、本质上 |
| 名词化 | 禁止「进行」「做出」「加以」「予以」：不写「进行粉碎」，写「粉碎」 |
| 短语动词 | 禁止「取下来」「放进去」「做出来」，写取下、放入、做出 |
| 自造对比框架 | 禁止「不是 X，（而）是 Y」：原文没有的对比不要现造 |

### 10.2 从 asd-ste100-zh 拿过来的四条（人读，脚本查不了）

1. **条件写在动作前。**「仅当备份完成且校验通过时，才删源文件。」不写「删源文件，前提是备份好了」。
   任务书里就是材料、机器、电压的门槛写在「造什么」之前。
2. **风险和禁令写在操作前，并保留后果的严重性。** 不写「注意安全」，写清不做这一步会卡在哪一格。
3. **要求强度和置信度不换算。**「必须 / 不得」「应当 / 建议」「可以」「可能 / 通常 / 已确认」各有含义，
   别把「应当」写成命令、把「可能」写成必然。玩家判断这一格能不能跳过的依据就是这个。
4. **不补原文没有的原因、频率、机制。** 写不清就去查配方和脚本，查不到就写「没查清」，
   不要用一句听起来合理的解释把格子填满。

这四条跟三段式不冲突：三段管**顺序**（是什么 → 为什么现在做 → 下一格接什么），
STE 管**每段内部**的条件、风险、强度。压到 25 字以内靠删套话，不靠删条件和数量。

### 10.3 同一个格子的两种写法

```
✗ 需要注意的是，双联粉碎机能够有效地提升粉末产出，从而为电炉、压缩与洗矿三条支线提供原料支撑。
✓ 双联粉碎机要单机、改良电动机、双插槽。还要一只改良机壳 138。
  铬粉、镍粉、铜粉都靠它磨。粉往电炉、压缩、洗矿三路走。

✗ 这台机器不是不能直接接 MFE 母线，而是需要先过一层变压器。
✓ 仅当电压够用时，这台机器才能直接接 MFE 母线。电压不够，先过一层变压器。
```

正文三段的分工：这一格是什么、为什么现在做、下一格接什么。不要「往后接：」这种收尾词，
DJ2 不这么写，直接把下一件事说完。

改完逐句对照一次原文：条件、否定、数值、单位、术语有没有在压缩时掉。这一步只能人看，词匹配查不出来。

```bash
python kubejs/tools/lint_quest_text.py     # 0 = 干净
```

## 11. 常见坑

- **新建章节文件** → id 全被重写、依赖全丢。唯一必须记住的坑。
- **手摆坐标** → 交叉、穿格、格子重叠。
- **`lang/zh_cn.snbt` 是 CRLF**，用 `io.open(..., newline='')` 读写，否则整份文件行尾被改写。
- **`check_js_balance.py` 要在 `kubejs/` 目录里跑**（内部用相对路径）。
- **两格同图标** → `--sync` 认不回来。
- **任务写了个没有配方的物品** → 玩家卡在这一格。
- **把 `ste-lint.py` 当中文体检** → 含汉字的输入直接返回退出码 2，等于什么都没查；中文一律走 `lint_quest_text.py`。
- **为了压到 25 字删掉条件** → 门槛、数量、否定都是内容，删了玩家就卡住；先拆句，再压。

## 12. 速查

```bash
# 改一格
vim kubejs/tools/l2_design.py            # 改 cell
python kubejs/tools/gen_l2_quests.py     # 生成
python kubejs/tools/check_quests.py      # 体检
python kubejs/tools/lint_quest_text.py   # 文案体检
# 游戏里：/ftbquests reload

# 把图调窄 / 调扁
vim kubejs/tools/l2_layout.py            # X_STEP / Y_STEP
```
